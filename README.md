# nova

스마트폰 사전예약 시스템 백엔드.

---

## 무엇을 만드나

오픈 직후 신청이 몰려도 사전예약을 안전하게 접수하고, **외부 예약 시스템의 처리를 기다리지 않고**
접수 결과를 안내한다. 접수된 예약은 백그라운드에서 외부에 등록하며, 서버가 중단됐다 복구되어도
유실 없이 최종 결과에 도달해야 한다.

```
모델·옵션 선택 → 영속 접수 → 접수 완료·순번 안내 → 백그라운드 외부 등록 → 예약 확정·배송 차수 안내
                    ▲                                        ▲
              여기서 응답한다                       사용자를 기다리게 하지 않는다
```

## 이것부터 이해해야 한다

**접수 완료 ≠ 외부 등록 완료.** 접수 완료는 "신청을 안전하게 받았다"는 뜻이지 외부 등록·구매·재고
확보가 끝났다는 뜻이 아니다. **일시적인 외부 호출 실패를 예약의 최종 실패와 같은 것으로 취급하지 않는다.**
이 구분이 설계 전체를 지배한다.

외부 Mock 은 평균 500ms 지연과 5% 실패를 재현한다. 여기서 5% 는 **외부 호출의 실패율**이지
전체 예약의 5% 를 최종 실패시키라는 뜻이 아니다. 외부 응답이 없으면 이미 등록됐을 가능성도 있으므로
원래 키로 결과를 확인한다.

---

## 확정된 업무 정책

**모델별 1인 1매** — 같은 모델은 색상·용량을 바꿔도 추가 신청 불가. 다른 모델은 각각 신청 가능.

**신청 단위** — 모델 하나의 옵션 하나, 수량 1.

**모집 구조** — 한 번의 사전예약 모집. 1차·2차·3차는 추가 모집이 아니라 배송 일정 구분이다.

**접수 순번** — 모델마다 독립적으로 1번부터. 다른 모델 신청 때문에 순번이 함께 증가하지 않는다.

**배송 차수** — 해당 모델의 접수 순번과 배송 구간으로 결정한다. **외부 등록 완료 순서로 배정하지 않는다.**

**중복 재전송** — 동일 신청의 재전송은 기존 접수 결과를 반환하며 새 예약·새 순번을 만들지 않는다.

**접수 성공 판정** — 신청이 안전하게 저장된 뒤에만 안내한다. 버튼 클릭만으로 성공을 표시하지 않는다.

**외부 확정 판정** — 실제 외부 등록 성공이 확인된 뒤에만 안내한다.

## 정해진 것

| 항목 | 결정 |
| --- | --- |
| 재신청 | 최종 실패·취소 후 재신청 허용. 단 진행 중·확정 예약은 모델당 1건 |
| 자동 재시도 실패 | DLQ 에 두고 관리자 확인·재처리. **DLQ 진입 자체가 예약 최종 실패가 아니다** |
| 배송 차수 개수 | 모델별로 관리자가 설정 |
| 접수 후 변경 | 해당 모델의 배송 기준과 기존 배정 변경 금지 |
| 오픈·마감 | 모델별로 따로 설정. 마감은 당일 자정 |
| 사용자 취소 | 포함 |
| 취소 가능 범위 | 배송 중부터 취소 불가. 그전까지 가능<br>(예약됨 → 배송 준비 중 → 배송 중 → 배송 완료) |
| 입장 대기열 | 포함. 진입 순서·대기 현황 제공 |
| 로그인 | 소셜 로그인만. 카카오 |
| 모델·옵션 관리 | 관리자 등록·편집 화면 포함 |
| 결제 | 사전예약 후 결제 기한을 주는 방식. "언제까지 결제하세요" |

## 아직 안 정해진 것

- 정합성 검사의 자동 실행 주기
- 불일치를 발견했을 때 후속 조치를 어디까지 자동화할지
- 자동 복구가 끝내 되지 않는 예약을 어떻게 종결할지
- 재시도·DLQ 상태를 사용자 화면과 관리자 화면 중 어디에 어떻게 표시할지
- 재신청할 때 접수 순번을 새로 줄지 기존 번호를 유지할지
- 배송일이 정해지지 않은 구간을 허용할지
- 옵션별 재고 관리와 접수 순서에 따른 배정을 사전예약에도 적용할지
- 알림 종류, 그리고 사용자가 끌 수 없는 알림을 둘지

## 범위

### 포함

- 가상 회원 선택 이용
- 외부 예약 시스템은 **팀이 만든 Mock 으로 대체** (500ms 지연 · 5% 실패, 시연 중 조절 가능)
- 외부 처리를 기다리지 않는 접수, 접수 데이터 보존, 중복 방지
- 비동기 외부 등록, 일시 실패 재시도, 중단 후 복구, 최종 결과 관리
- 사용자 화면 — 신청, 접수 결과, 예약 목록·상세, 처리 상태·순번·배송 차수
- 관리자 화면 — 예약·실패 내역, 처리 현황, Mock 설정, 정합성 배치 관리
- 정합성 검사 — 두 시스템 결과 대조, 불일치 보고, 재검사·전후 비교

### 제외

- 추가 모집·사전예약 회차 생성 (한 번의 모집으로 제한)
- 실제 PG·통신사·문자/이메일 연동 (전부 Mock)
- 배송 추적·송장·배송 완료 관리 (배송 차수·예상 일정 안내까지만)

## 검증 기준

요구사항을 충족했는지 확인할 주요 시나리오다.

- **정상 흐름** — 접수 완료와 확정을 구분해서 안내하고 예약번호·순번·배송 정보를 보여준다
- **중복 방지** — 같은 모델의 색상·용량을 바꿔 동시 신청해도 예약이 중복 생성되지 않는다
- **멱등성** — 같은 키의 재전송은 기존 결과를 반환하고, 같은 키·다른 내용은 거절한다
- **응답 유실** — 저장 후 응답을 잃거나 새로고침해도 원래 예약을 다시 찾을 수 있고 순번이 중복되지 않는다
- **외부 일시 실패** — 재시도로 성공에 도달하며, 호출 실패를 최종 실패로 즉시 노출하지 않는다
- **중단·재기동** — 처리 서버가 죽었다 살아나도 유실 없이 처리가 이어지고 외부 중복 등록이 없다
- **배송 배정** — 외부 확정 순서가 접수 순서와 달라도 모델별 순번 기준으로 배정된다
- **정합성 검사** — 불일치를 양방향으로 검출하고, 검사 자체는 업무 데이터를 바꾸지 않는다
- **검사 미완료 구분** — 외부 조회 실패나 목록 누락이 있으면 "정상"으로 판정하지 않는다
- **접근 제어** — 타인 예약과 관리자 기능 접근이 차단되고 민감정보가 노출되지 않는다
- **트래픽** — 오픈 직후 집중 신청을 부하 시험으로 재현한다 (과제 예시 10초 5,000건)

## mock-api

외부 예약 시스템(통신사 예약 서버) 역할을 대신하는 Mock 서버. 포트는 **8081** 이고
본 서비스(`be` 저장소)는 8080 이다. 요구사항 5.4 의 계약을 구현한다.

> **현재 상태:** 예약 등록 · 번호 조회 · 키 조회 · 설정 조회·변경 · 지연·실패 주입까지 구현됐다.
> 취소 · 결함 주입 · 초기화는 아래 계약대로 구현할 예정이다.

업무 호출은 **HTTP 로만** 한다. 다만 **정합성 검사는 예외로 `external_mock` 스키마를 읽기 전용으로
직접 조회한다**(팀 결정, 요구사항 2.3 · 6.1). 대조를 위한 전체 목록 API 를 만들지 않는 대신,
검사가 실패한 실행도 보고서 파일로 남겨 "조회 실패" 를 "불일치 0건" 으로 표시하지 않는다.

**Mock 은 프로세스 1개로 띄운다.** 지연·실패 설정과 결함이 메모리에 있어 2개 이상이면
설정 변경이 한쪽에만 적용되고, 결함을 건 키의 요청이 다른 쪽으로 가면 발동하지 않는다.
등록 기록은 DB 라 영향이 없다.

### 실행

```bash
cp .env.example .env                                                               # DB 계정 · 포트
cp src/main/resources/application.yml.example src/main/resources/application.yml   # 접속 정보
docker compose up -d mysql       # external_mock database 가 만들어진다 (로컬 전용, 포트 3307)
./gradlew bootRun                # http://localhost:8081
```

**그대로 복사하면 그대로 뜬다.** 접속 정보가 `.env`(컨테이너가 만드는 계정)와
`application.yml`(앱이 접속하는 계정) 두 군데에 나뉘어 있으니, 포트나 비밀번호를 바꾸려면
**양쪽을 같이** 고친다.

저장소는 MySQL `external_mock` database 다. 본 서비스와 **같은 인스턴스의 다른 database** 이며
cross-database 조회나 물리 FK 를 두지 않는다. 재기동해도 등록 기록이 유지된다(5.4 기록 보존).
`compose.yaml` 은 Mock 만 따로 개발할 때 쓰는 것이고, 통합할 때는 본 서비스 쪽 인스턴스에
`external_mock` database 를 만들어 붙인다.

지연·실패율 설정은 테이블에 두지 않으므로 **재기동하면 기본값(500ms / 5%)으로 돌아간다.**
요구사항이 요구하는 것은 "재기동 없이 변경"이지 "재기동 후 유지"가 아니고,
시연은 매번 같은 초기 상태에서 시작하는 편이 낫기 때문이다.

### API — 8개

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/external/reservations` | 예약 등록 (멱등) |
| GET | `/external/reservations/{externalNumber}` | 번호로 단건 조회 |
| GET | `/external/reservations/by-key/{externalKey}` | 키로 등록 상태 조회 |
| POST | `/external/cancellations` | 예약 취소 |
| GET · PUT | `/external/config` | 지연·실패 설정 조회 · 변경 |
| POST | `/external/faults` | 결함 주입 (응답 유실) |
| POST | `/external/reset` | 기록 초기화 |

**요청 본문에 계약에 없는 필드가 있으면 `400 INVALID_REQUEST` 다.** 모르는 필드를 조용히 버리면
설정 API 에 없는 값을 넣어도 200 이 나와 적용된 줄 알게 되고, 워커가 계약과 다른 본문을 보내도
아무도 모른다. 오류 메시지에 틀린 필드 이름과 받을 수 있는 필드, enum 이면 허용값을 담는다.

```
timeoutHoldMs 은(는) 알 수 없는 필드입니다. 받을 수 있는 필드: registerLatencyMs, failureRate, failureMode
failureMode 은(는) HTTP_5XX, TIMEOUT 중 하나여야 합니다. 받은 값: HTTP_429
```

#### 예약 등록 (멱등)

```bash
curl -X POST localhost:8081/external/reservations \
  -H 'Idempotency-Key: 9f1c2d3e-4a5b-6c7d-8e9f-0a1b2c3d4e5f' \
  -H 'Content-Type: application/json' \
  -d '{"customerId":1001,"productId":12,"sku":"SM-G999-256-BLK"}'
```

| 상황 | 응답 |
| --- | --- |
| 최초 요청 | `201` + 새 `externalNumber` |
| 같은 키 · 같은 내용 | `201` + **같은** `externalNumber` + `X-Idempotent-Replay: true` |
| 같은 키 · 다른 내용 | `422 KEY_PAYLOAD_MISMATCH` |
| 취소 표식이 있는 키 | `409 KEY_CANCELED` |

멱등 키는 본 서비스의 `preorders.preorder_token` 이다. 동일 내용 판정은 JSON 문자열이 아니라
**저장된 `customer_id` · `product_id` · `sku` 를 직접 비교**한다(요구사항 5.3, ERD). 지문(해시) 칸을
두지 않아 어느 필드가 달라 거절됐는지 응답에 담을 수 있다.

#### 조회

```bash
curl localhost:8081/external/reservations/R-20260916-0048213579      # 번호로 단건
curl localhost:8081/external/reservations/by-key/9f1c2d3e-...        # 키로 상태
```

키 조회는 **잠금 읽기**로 한다. 커밋 안 된 등록을 못 본 채 404 를 돌려주면 워커가 재등록해
중복 등록이 된다. 잠금 읽기여야 "404 = 등록 안 됨" 이 확정 근거가 된다.

#### 취소

```bash
curl -X POST localhost:8081/external/cancellations \
  -H 'Content-Type: application/json' \
  -d '{"externalKey":"9f1c2d3e-...","reason":"GHOST_COMPENSATION"}'
```

미등록 키도, 이미 취소된 건도 `200` 이다. **등록이 없어도 취소 표식 행을 남긴다** — 표식이 없으면
"취소 성공" 이라고 응답해놓고 늦게 도착한 등록이 살아나는 상태가 된다.

#### 지연·실패율 변경 (시연용)

```bash
curl localhost:8081/external/config
curl -X PUT localhost:8081/external/config -H 'Content-Type: application/json' \
  -d '{"registerLatencyMs":2000,"failureRate":0.5,"failureMode":"HTTP_5XX"}'
```

서버 재기동 없이 즉시 적용되며, 응답으로 **실제 적용값**을 돌려준다.
설정·조회·취소 경로에는 지연·실패를 주입하지 않으므로 실패율 100% 상태에서도 되돌릴 수 있다.

기본값은 `application.yml` 의 `mock.*` (500ms / 5%).

#### 결함 주입

```bash
curl -X POST localhost:8081/external/faults -H 'Content-Type: application/json' \
  -d '{"externalKey":"9f1c2d3e-...","faultType":"RESPONSE_LOST_AFTER_COMMIT"}'
```

등록을 커밋한 뒤 응답 없이 연결을 끊는다. **지연·실패율로는 이 상황을 만들 수 없다** —
주입한 실패는 모두 커밋 전이라 등록이 저장되지 않기 때문이다. 한 번 발동하면 자동 해제된다.

**결함은 새로 커밋되는 등록에만 걸린다.** 이미 등록된 키에 걸면 재생 요청에는 커밋이 없어 발동하지
않고 그대로 남는다. 남은 결함은 `POST /external/reset` 이 지운다.

### 구조

```
com.grandis.nova.mockapi/
├── global/
│   ├── chaos/      설정 스냅샷 · 지연·실패 주입 · 결함 (인터페이스 + 임시 구현)
│   ├── config/     MockProperties (지연·실패율·타임아웃 유지 시간 기본값)
│   └── error/      오류 코드 · 응답 형식 · 예외 핸들러
├── registration/   등록 원장 — 등록 · 조회 · 취소 · 멱등 판정 · 채번
└── admin/          설정 · 결함 주입 · 초기화 API
```

지연·실패 주입은 **등록 처리 안에서** 부른다. 필터에 두면 조회·취소에도 걸리는데, 과제가 취소를
"항상 성공" 으로 가정하고 정합성 조회까지 느려지기 때문이다. 대기는 **트랜잭션 밖**에서 한다 —
트랜잭션 안에서 기다리면 DB 커넥션이 그만큼 묶여 풀이 마른다.

등록 처리 순서는 이렇다.

```
[트랜잭션 밖]  1. 지연 대기   2. 실패율 판정(커밋 전이라 저장 없음)
[트랜잭션 안]  3. 키 행 잠금   4. 취소 표식이면 KEY_CANCELED
               5. 이미 등록됐으면 재생 / 내용 다르면 422
               6. 커밋 후 201   7. 결함이 걸려 있으면 응답 없이 연결 끊기
```

같은 새 키로 등록과 취소가 동시에 들어오면 한쪽이 중복 키(1062)를 받는다. **오류가 아니라
정상 분기다** — 다시 잠금 읽기로 조회해 이어간다. 이 설계는 READ COMMITTED 전제이므로
`application.yml` 과 `compose.yaml` 양쪽에서 격리 수준을 지정한다.

### 등록 파트 ↔ 제어 파트 계약

등록 처리(`registration/`)가 제어 파트(`global/chaos/`)에서 가져다 쓰는 것은 이 넷뿐이다.
**시그니처나 아래 약속을 바꾸려면 양쪽이 합의한다.**

| 쓰는 것 | 언제 | 약속 |
| --- | --- | --- |
| `ConfigProvider.snapshot()` | 1단계 전 | 이 시도가 끝까지 쓸 설정을 얼려 준다. 버전은 `X-Mock-Config-Version` 으로 나간다 |
| `FailureInjector.apply(snapshot)` | 1~2단계 | **트랜잭션 밖**에서 부른다. 실패는 `MockException`, `TIMEOUT` 은 응답 없이 끝난다 |
| `FaultHook.consumeResponseLost(key)` | 7단계 | **새로 커밋한 직후에만** 부른다. true 면 결함을 소비한 것이다 |
| `ConnectionDropper.drop(reason)` | 7단계 | 응답 없이 연결을 붙잡다 끝낸다. **정상 반환하지 않는다** — 항상 `ResponseLostException` |

`drop()` 이 정상 반환하지 않는다는 것도 계약이다. 등록 처리가 여기에 기대어 뒤이은 201 응답을 쓰지 않는다.

### 스키마

`docs/schema.sql` 이 정본이다. Hibernate 가 테이블을 만들면 CHECK 제약이 빠지므로
`ddl-auto` 는 `validate` 로 둔다. 칸을 바꿀 때는 엔티티와 이 파일을 함께 고친다.

### 테스트

```bash
./gradlew test
```

테스트에서는 `src/test/resources/application.yml` 이 H2 인메모리로,
지연·실패율을 0 으로 덮어쓴다.

> **주의:** H2 는 컨텍스트 로딩 확인용이다. 멱등 등록의 동시성은 잠금과 중복 키 동작에 기대므로
> H2 에서 통과해도 MySQL 에서 통과한다는 보장이 없다. 동시성 테스트는 MySQL 로 돌린다.

**Docker 가 켜져 있으면 MySQL 시험(Testcontainers)도 같이 돈다.** 없으면 그 시험만 건너뛰므로,
동시성을 건드렸으면 Docker 를 켜고 돌린다.

구현 시 최소한 다음 6가지는 검증해야 한다.

- 같은 키·같은 내용의 재요청이 같은 예약번호를 반환하는가
- 같은 키·다른 내용을 422 로 거절하는가
- 같은 키로 동시에 10건을 보내도 등록이 1건인가 (**100회 반복**해야 의미가 있다)
- 취소를 반복해도, 미등록 키를 취소해도 성공으로 처리하는가
- 취소 뒤 늦게 도착한 등록이 `KEY_CANCELED` 로 막히는가
- 실패율 100% 에서도 설정 API 로 되돌릴 수 있는가

## 브랜치

에픽 브랜치 아래에 작업 브랜치를 둔다.

```
main
 └── epic/NV-1                  에픽. main 에서 딴다
      ├── feature/NV-2          작업. 에픽에서 따고 에픽으로 합친다
      ├── feature/NV-3
      └── fix/NV-4
```

작업 브랜치는 **에픽에서 따고 에픽으로 PR** 을 올린다. `main` 으로 직접 올리지 않는다.
에픽이 끝나면 에픽 → `main` PR 을 올린다.

브랜치 이름은 `<타입>/<이슈 키>` 다. 설명을 붙이고 싶으면 하이픈으로 잇는다.

```
epic/NV-1
feature/NV-7
feature/NV-7-kakao-login
fix/NV-12
```

머지는 **작업 → 에픽, 에픽 → `main` 모두 merge commit** 으로 한다.
작업 브랜치에서 쌓은 커밋이 그대로 보존되므로, 나중에 어느 단계에서 무엇이 바뀌었는지 되짚을 수 있다.

PR 은 최소 1명이 승인해야 머지한다.

에픽이 길어지면 `main` 과 벌어진다. **주기적으로 `main` 을 에픽에 반영해** 충돌을 미리 푼다 —
에픽 → `main` PR 에서 한꺼번에 터지면 풀기 어렵다.

## 커밋

`<type>(<이슈 키>): <요약>` 형식. 요약은 한국어로 쓰고 마침표를 붙이지 않는다.

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드·설정·의존성 |

```
feat(NV-7): 사전예약 접수 API 추가
fix(NV-12): 같은 멱등키 동시 재전송 시 순번이 두 번 소비되는 문제 수정
chore(NV-3): mock-api MySQL 전환
```

이슈 키는 **그 커밋이 속한 작업**의 키다. 에픽 키가 아니다.

**리뷰 반영 커밋에는 이슈 키를 붙이지 않는다.**

```
fix: 리뷰 반영 — 중복 검증을 서비스로 옮김
refactor: 리뷰 반영 — 조건부 UPDATE 1행 확인 추가
```

PR 자체가 이미 이슈에 묶여 있어 키가 중복 정보이기 때문이다.

머지를 squash 하지 않으므로 이 커밋들도 히스토리에 그대로 남는다.
그래서 **"리뷰 반영"만 쓰지 말고 무엇을 고쳤는지 함께 적는다.**

**한 커밋에 한 가지 일만 담는다.** 기능과 리팩터링이 섞이면 리뷰에서 무엇이 바뀐 건지 가려낼 수 없다.
