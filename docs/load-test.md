# 부하 시험 — 방법과 결과

| 항목 | 내용 |
| --- | --- |
| 대상 | 외부 예약 Mock (`mock-api`) · `POST /external/reservations` |
| 실행 | `./gradlew loadTest --args="http://localhost:8081 <시나리오>"` |
| 시나리오 | `baseline` · `latency` · `timeout` |
| 실행일 | 2026-09-27 |
| 상태 | **탐색 실행.** 조건이 팀 합의를 거치지 않아 성능 합격 판정의 근거로 쓸 수 없다 |

## 왜 자작 클라이언트인가

과제가 *"도구 자유(JMeter · k6 · 자작 클라이언트 등). 도구·처리량은 평가하지 않음"* 으로 정했다.
그중 자작을 택한 이유는 둘이다.

- **추가 설치가 없다.** 인수인계 문서의 설치 목록이 JDK · Docker · Git 뿐이라, 도구를 늘리면
  넘겨받는 사람의 준비 과정이 그만큼 길어진다.
- **결과 불명과 명시적 거절을 직접 구분해야 한다.** 이 프로젝트에서 두 가지는 뜻이 정반대인데
  (거절은 결과가 정해진 것, 결과 불명은 등록됐을 수도 있어 `by-key` 조회가 필요한 것)
  일반 부하 도구는 둘을 모두 "error" 로 묶는다.

도구를 나중에 바꿔도 비용이 작다. 하네스는 `src/test/java/.../load/` 안에만 있고 `src/main` 을
건드리지 않으며, 아래 분류 정의와 보고서 형식은 도구와 무관하게 그대로 쓸 수 있다.

## 요청을 네 분류로 센다

요구사항 8장이 실패와 미전송을 결과에서 빼지 말라고 정했다. 성공률을 "응답받은 것 중 성공" 으로
세면 보내지도 못한 요청과 결과를 모르는 요청이 분모에서 사라져, **서버가 버티지 못한 상황이
오히려 좋은 숫자로 나온다.** 그래서 네 분류의 합이 항상 보낸 요청 수와 같도록 센다.

| 관측 | 분류 | 뜻 |
| --- | --- | --- |
| 201 | 접수 성공 | 등록됨(재생 포함) |
| 400 · 409 · 422 · 500 | 명시적 거절 | 응답을 받았으므로 **등록 안 된 것이 확정** |
| 읽기 타임아웃 · 응답 없음 | **결과 불명** | 등록됐을 수도 있다. `by-key` 조회로 확인해야 한다 |
| 연결 거부 · 연결 타임아웃 | 미전송 | 서버가 받지 못했다. 부하를 걸지 못한 것이다 |

> **합의 대기:** 500(주입된 일시 실패)을 "명시적 거절" 에 넣었다. 명세상 500 은 커밋 전이라
> 등록되지 않은 것이 확정이고 응답도 받았기 때문이다. 팀이 "일시 실패는 별도" 로 보길 원하면
> 바꿔야 하는데, **정의를 바꾸면 이전 결과와 비교가 불가능해지므로** 먼저 확인이 필요하다.

## 가설

1. 접수 성공 + 결과 불명의 합이 DB 실제 등록 건수와 같을 것이다 —
   500 은 커밋 전 실패이므로 아무것도 저장하지 않는다는 명세의 약속이 지켜진다면.
2. 관측 응답 지연이 설정한 `registerLatencyMs` 와 비슷할 것이다 —
   Mock 이 병목이 아니라면. 크게 벗어나면 "우리 서버가 느린 것" 과 구분할 수 없게 된다.
3. `failureMode=TIMEOUT` 이면 아무것도 저장되지 않을 것이다 — 커밋 전 실패이므로.

## 측정

실행 환경: Windows 10 · 6코어 · JDK 25 · 클라이언트와 Mock 이 같은 PC · MySQL 8.4 (Docker).
각 시나리오 5,000건을 10초에 걸쳐 고르게 발사, 응답 타임아웃 3초.

| | `baseline` | `latency` | `timeout` |
| --- | --- | --- | --- |
| 설정 | 500ms · 5% | 2000ms · 0% | 0ms · 100% · TIMEOUT |
| 접수 성공 | **4,698 (94.0%)** | 396 (7.9%) | 0 |
| 명시적 거절 | 256 (5.1%) | 0 | 0 |
| **결과 불명** | 46 (0.9%) | **4,604 (92.1%)** | **5,000 (100%)** |
| 미전송 | 0 | 0 | 0 |
| **DB 실제 등록** | **4,744** | **5,000** | **0** |
| p95 / p99 | 2517 / 2541ms | 2945 / 2993ms | 측정 불가 |
| 최대 동시 요청 | — | 1,508 | 1,526 |

## 해석

### 가설 1 — 맞았다. 계약이 규모에서도 지켜진다

`baseline` 의 산술이 정확히 맞는다.

```
접수 성공 4,698 + 결과 불명 46 = 4,744 = DB 실제 등록
```

500 을 받은 **256건은 DB 에 한 건도 남지 않았다.** *"실패는 커밋 전에 발생한다. 아무것도 저장하지
않는다"* 는 명세의 약속이 5,000건 규모에서 지켜졌다는 뜻이다. 관측 실패율 5.1% 도 설정한 5% 와
일치한다.

`timeout` 시나리오도 같다 — 100% 결과 불명인데 DB 는 0건이다(가설 3도 맞았다).

### 가설 2 — 틀렸다. 다만 원인을 아직 특정할 수 없다

`latency` 는 설정 2000ms 인데 p95 가 2945ms 였고, `baseline` 은 설정 500ms 인데 p95 가 2517ms 였다.
관측 지연이 설정값보다 훨씬 크다.

**그러나 이 실행으로는 "Mock 이 병목" 이라고 결론 낼 수 없다.** 교란 요인이 셋이다.

- **클라이언트와 Mock 이 같은 6코어 PC 에 있다.** 서로 CPU 를 뺏는다.
- **응답 타임아웃 3초 vs 설정 지연 2000ms** — 여유가 1초뿐이라 조금만 밀려도 타임아웃이 된다.
- **p95 · p99 가 타임아웃 값에 붙어 있다.** 느린 요청이 집계에서 빠진 잘린 분포라 실제가 아니다.

셋 다 합의 항목(환경 · 관찰 종료 조건 · 응답 지연 기준)에 해당한다. 판별을 제대로 하려면
클라이언트를 다른 장비로 빼거나, 응답 타임아웃을 설정 지연보다 충분히 크게 잡아야 한다.

### 이번 실행에서 가장 중요한 발견

`latency` 시나리오에서 **결과 불명 4,604건이 전부 실제로는 등록에 성공**했다. DB 에 5,000건이
모두 있었다.

워커가 타임아웃을 실패로 보고 재등록했다면 **중복 등록 4,604건**이 났을 상황이다. 과제가 요구한
*"외부 시스템이 느리거나 실패해도 같은 예약이 두 번 등록되어서는 안 된다"* 가 왜 어려운지,
그리고 `GET /external/reservations/by-key/{externalKey}` 가 왜 필수인지를 숫자로 보여준다.

**5% 확률에 기대서는 이 장면을 만들 수 없다.** 지연을 키워 타임아웃을 대량으로 유도했기 때문에
드러났다.

### 톰캣 연결 쌓임은 이 규모에서 일어나지 않았다

명세는 *"1,000 RPS · `failureRate=1.0` 이면 유지 10초에 약 1만 개로 톰캣 기본 최대 연결(8,192)을
넘는다"* 고 계산해 두었다. 이번 실행은 500 RPS · 유지 5초라 **최대 동시 1,526** 에 그쳤다.
상한 초과를 검증하려면 규모나 유지 시간을 키워야 하고, 그것도 합의 항목이다.
