# 부하 시험 — 방법과 결과

| 항목 | 내용 |
| --- | --- |
| 대상 | 외부 예약 Mock (`mock-api`) · `POST /external/reservations` |
| 실행 | `./gradlew loadTest --args="http://localhost:8081 <시나리오>"` |
| 시나리오 | `baseline` · `latency` · `timeout` |
| 실행일 | 2026-09-27 |
| 상태 | **탐색 실행.** 조건이 팀 합의를 거치지 않아 성능 합격 판정의 근거로 쓸 수 없다 |

## 왜 자작 클라이언트인가

과제가 *"도구 자유(JMeter · k6 · 자작 클라이언트 등). 도구·처리량은 평가하지 않음"* 으로 정했다.
그중 자작을 택한 이유는 둘이다.

- **추가 설치가 없다.** 인수인계 문서의 설치 목록이 JDK · Docker · Git 뿐이라, 도구를 늘리면
  넘겨받는 사람의 준비 과정이 그만큼 길어진다.
- **결과 불명과 명시적 거절을 직접 구분해야 한다.** 이 프로젝트에서 두 가지는 뜻이 정반대인데
  (거절은 결과가 정해진 것, 결과 불명은 등록됐을 수도 있어 `by-key` 조회가 필요한 것)
  일반 부하 도구는 둘을 모두 "error" 로 묶는다.

도구를 나중에 바꿔도 비용이 작다. 하네스는 `src/test/java/.../load/` 안에만 있고 `src/main` 을
건드리지 않으며, 아래 분류 정의와 보고서 형식은 도구와 무관하게 그대로 쓸 수 있다.

## 요청을 다섯 분류로 센다

요구사항 8장이 실패와 미전송을 결과에서 빼지 말라고 정했다. 성공률을 "응답받은 것 중 성공" 으로
세면 보내지도 못한 요청과 결과를 모르는 요청이 분모에서 사라져, **서버가 버티지 못한 상황이
오히려 좋은 숫자로 나온다.** 그래서 합이 항상 보낸 요청 수와 같도록 센다.

분류의 기준은 "응답을 받았는가" 가 아니라 **본 서비스가 무엇을 해야 하는가** 다.

| 관측 | 분류 | 본 서비스가 할 일 | 8장 분류 |
| --- | --- | --- | --- |
| 201 | 접수 성공 | 확정 반영 | 접수 성공 |
| 400 · 409 · 422 | 명시적 거절 | 재시도하지 않고 정리 | 명시적 거절 |
| 5xx | **일시 실패** | **재시도** | 명시적 거절 |
| 읽기 타임아웃 · 응답 없음 | **결과 불명** | `by-key` 로 확인한 뒤 판단 | 결과 불명 |
| 연결 거부 · 연결 타임아웃 | 미전송 | 다시 보낸다 | 미전송 |

**8장의 네 분류에서 "명시적 거절" 을 둘로 나눴다.** 처음에는 "응답을 받았으니 결과가 확정됐다" 로
보고 500 을 거절에 넣었는데, NV-23 리뷰에서 지적을 받아 고쳤다. 400 · 409 · 422 는 다시 보내도
결과가 같은 확정 거절이고 5xx 는 재시도 대상이라 **뜻이 정반대**이며, 명세도 "5xx 는 미등록의
증거가 아니다" 로 둔다. 합쳐 두면 **설정한 실패율이 실제로 몇 % 나왔는지가 거절 수에 묻힌다.**

실제로 나눠 보니 바로 드러났다 — `baseline` 의 일시 실패가 251건(5.0%)으로 설정한 `failureRate`
0.05 와 정확히 맞는다. 합쳐 뒀을 때는 이 값이 보이지 않았다.

다섯으로 나눠도 합이 보낸 요청 수와 같다는 성질은 그대로다.

## 가설

1. 접수 성공 + 결과 불명의 합이 DB 실제 등록 건수와 같을 것이다 —
   500 은 커밋 전 실패이므로 아무것도 저장하지 않는다는 명세의 약속이 지켜진다면.
2. 관측 응답 지연이 설정한 `registerLatencyMs` 와 비슷할 것이다 —
   Mock 이 병목이 아니라면. 크게 벗어나면 "우리 서버가 느린 것" 과 구분할 수 없게 된다.
3. `failureMode=TIMEOUT` 이면 아무것도 저장되지 않을 것이다 — 커밋 전 실패이므로.

## 측정

실행 환경: Windows 10 · 6코어 · JDK 25 · 클라이언트와 Mock 이 같은 PC · MySQL 8.4 (Docker).
각 시나리오 5,000건을 10초에 걸쳐 고르게 발사, 응답 타임아웃 3초, 관찰 종료 30초.

**DB 건수는 서버가 잦아든 뒤에 셌다.** 그 이유는 아래 "측정 방법에서 걸린 것" 에 적었다.

| | `baseline` | `latency` | `timeout` |
| --- | --- | --- | --- |
| 설정 | 500ms · 5% | 2000ms · 0% | 0ms · 100% · TIMEOUT |
| 접수 성공 | **4,082 (81.6%)** | **4,938 (98.8%)** | 0 |
| 명시적 거절 | 0 | 0 | 0 |
| **일시 실패 (5xx)** | **251 (5.0%)** | 0 | 0 |
| **결과 불명** | 667 (13.3%) | 62 (1.2%) | **5,000 (100%)** |
| 미전송 | 0 | 0 | 0 |
| **DB 실제 등록** | **4,749** | **5,000** | **0** |
| p95 / p99 | 2405 / 2922ms | 2836 / 2852ms | 측정 불가 |
| 최대 동시 요청 | 1,009 | 1,420 | 1,524 |

### 측정 방법에서 걸린 것 — 클라이언트가 멈춰도 서버는 계속 처리한다

처음에는 `loadTest` 가 끝나자마자 DB 를 셌는데, 시나리오를 연달아 돌리자 **`timeout` 실행에 135건이
남는** 이상한 결과가 나왔다. TIMEOUT 은 커밋 전 실패라 0 이어야 하는데도.

앞 시나리오에서 **관찰 창을 넘겨 클라이언트가 포기한 요청들이 서버에서는 계속 돌다가 나중에
커밋된 것**이었다. `baseline` 도 클라이언트 종료 직후엔 4,527건이었다가 잦아든 뒤 4,749건이 됐다.
222건이 그 뒤에 커밋됐다는 뜻이다.

그래서 **행 수가 8초 동안 변하지 않을 때까지 기다린 뒤** 센다. 이걸 놓치면 시나리오 사이에 결과가
섞여 엉뚱한 결론이 나온다.

## 해석

### 가설 1 — 맞았다. 계약이 규모에서도 지켜진다

세 시나리오 모두 산술이 맞는다.

```
baseline   접수 4,082 + 결과 불명   667 = 4,749 = DB 실제 등록
latency    접수 4,938 + 결과 불명    62 = 5,000 = DB 실제 등록
timeout    접수     0 + 결과 불명 5,000 =     0 = DB 실제 등록   ← 아래 참조
```

`baseline` 에서 5xx 를 받은 **251건은 DB 에 한 건도 남지 않았다.** *"실패는 커밋 전에 발생한다.
아무것도 저장하지 않는다"* 는 약속이 5,000건 규모에서 지켜졌다. 그 251건은 설정한 `failureRate`
0.05 와 정확히 맞는 5.0% 다.

### 가장 중요한 발견 — "결과 불명" 은 하나가 아니다

`timeout` 의 산술만 어긋나 보인다. 결과 불명 5,000건인데 DB 가 0건이다. **어긋난 게 아니라
원인이 다르다.**

| | 결과 불명 | DB 에 남았나 | 원인 |
| --- | --- | --- | --- |
| `latency` | 62건 | **전부 남음** | 커밋은 끝났고 응답만 늦어 클라이언트가 포기 |
| `timeout` | 5,000건 | **하나도 없음** | 커밋 전에 연결을 붙잡고 끊음 |

**클라이언트가 보는 것은 양쪽 다 "응답 없음" 으로 똑같다.** 그런데 하나는 등록됐고 하나는 안 됐다.

이것이 `GET /external/reservations/by-key/{externalKey}` 가 왜 필수인지다. 결과 불명일 때 워커가
할 수 있는 판단은 "다시 보낸다" 뿐인데, `latency` 쪽이었다면 그 재시도가 **중복 등록**이 된다.
멱등 키가 그걸 막고, `by-key` 조회가 그걸 미리 확인하게 해준다.

과제가 요구한 *"외부 시스템이 느리거나 실패해도 같은 예약이 두 번 등록되어서는 안 된다"* 가 왜
어려운지를 숫자로 보여주는 장면이다.

### 가설 2 — 관측 지연은 여전히 설정값보다 크다. 다만 원인을 특정할 수 없다

`latency` 는 설정 2000ms 인데 p95 2836ms, `baseline` 은 설정 500ms 인데 p95 2405ms 다.

**그러나 이 실행으로 "Mock 이 병목" 이라고 결론 낼 수 없다.** 교란 요인이 셋이다.

- **클라이언트와 Mock 이 같은 6코어 PC 에 있다.** 서로 CPU 를 뺏는다.
- **응답 타임아웃 3초 vs 설정 지연 2000ms** — 여유가 1초뿐이라 조금만 밀려도 타임아웃이 된다.
- **p95 · p99 가 타임아웃 값 근처에 몰려 있다.** 느린 요청이 집계에서 빠진 잘린 분포다.

셋 다 합의 항목(환경 · 관찰 종료 조건 · 응답 지연 기준)에 해당한다. 판별을 제대로 하려면
클라이언트를 다른 장비로 빼거나, 응답 타임아웃을 설정 지연보다 충분히 크게 잡아야 한다.

### 첫 실행과 숫자가 크게 다른 이유 — 예열

같은 `latency` 설정으로 처음 돌렸을 때는 접수 성공이 **396건(7.9%)** 이었는데, 이번에는
**4,938건(98.8%)** 이다. 설정도 코드도 같다.

차이는 **JVM 이 식어 있었는지**다. 첫 실행은 `bootRun` 직후였고, 이번에는 `baseline` 5,000건을
이미 처리해 JIT 컴파일과 커넥션 풀이 데워진 뒤였다.

**따라서 판정 실행에서는 예열 구간을 조건에 넣어야 한다.** 이것도 합의 항목에 추가할 내용이다 —
첫 실행의 92% 타임아웃을 "Mock 이 느리다" 로 읽었다면 잘못된 결론이었을 것이다.

### 톰캣 연결 쌓임은 이 규모에서 일어나지 않았다

명세는 *"1,000 RPS · `failureRate=1.0` 이면 유지 10초에 약 1만 개로 톰캣 기본 최대 연결(8,192)을
넘는다"* 고 계산해 두었다. 이번 실행은 500 RPS · 유지 5초라 **최대 동시 1,524** 에 그쳤다.
상한 초과를 검증하려면 규모나 유지 시간을 키워야 하고, 그것도 합의 항목이다.

## 합의된 것

| 항목 | 결정 | 출처 |
| --- | --- | --- |
| 5xx 를 "일시 실패" 로 따로 센다 | 확정 | NV-23 리뷰 |
| 관찰 종료 조건 30초 | 확정 | 〃 |
| **관찰 종료 조건 > 요청 응답 타임아웃** | 확정 · **코드가 강제한다** | 〃 |

마지막 조건은 `LoadPlan` 생성자에서 검사한다. 짧게 잡으면 아직 자기 타임아웃이 오지 않은 요청이
관찰 창 때문에 잘려 결과 불명으로 세어지는데, 그러면 측정하려던 것이 아니라 시험 설정이 만들어낸
숫자가 된다.
